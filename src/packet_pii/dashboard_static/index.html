What TRACE does

TRACE reads a packet capture, rebuilds the unencrypted HTTP conversations inside it and checks each request and response for personal information.

  • Findings lists each detected item with its value masked.
  • Evidence inspector shows the request, response, field and packets behind a finding.
  • Network traffic lists every TCP flow and HTTP message.

Encrypted (HTTPS/TLS) traffic is not decrypted, so its contents are not inspected.

                      Getting started

                      1. Choose a detection method. Rules only is selected by default. Hybrid also runs the contextual model when one is loaded.
                      2. Choose a capture. Drop a .pcap or .pcapng file on the Overview page, or run the sample analysis. Progress appears at the top of the page and can be cancelled.
                      3. Review findings. Open Findings and select a row. The evidence inspector shows the request, the response and the packets behind it.
                      4. Export the report. Use Export report in the top bar to download the JSON report. Values stay masked.

                      Limits to keep in mind

                      • Encrypted traffic is not read. TRACE does not decrypt TLS. HTTPS contents are not inspected.
                      • No finding does not mean no personal data. Unsupported protocols, gaps in the capture and processing limits can hide evidence.
                      • Findings are candidates. A finding does not prove identity, misuse or exfiltration.
                      • Scores are not accuracy. Rule scores are heuristics. Model scores are uncalibrated.
                      • Response bodies are not kept. TRACE records where a body sits in the stream and what was extracted from it, not the page itself.

                      Terms used in TRACE

                      Packet
                      One frame recorded in the capture file. A single web request can span many packets.
                      TCP flow
                      All TCP traffic between two endpoints, for example 10.0.0.5:51344 and 93.184.216.34:80.
                      Stream direction
                      One side of a flow, reassembled in order. The client-to-server direction carries requests; the reverse carries responses.
                      HTTP message
                      A single request (such as POST /login) or response (such as HTTP/1.1 200).
                      Transaction
                      A request matched to its response. Matching is best-effort for HTTP/1 and by stream ID for HTTP/2.
                      Field
                      A value TRACE extracted from a message: a header, query parameter, form value, JSON value or text body.
                      Finding
                      A field, or part of one, that looks like personal information, such as an email address in a form field.
                      Rules and model
                      Rules match known formats and field names. The optional model suggests names and usernames from context.
                      Masking
                      Detected values are shown partly hidden, for example j***@example.com, in the interface and the report.
                      Incomplete analysis
                      Capture damage, stream gaps or processing limits meant some traffic could not be fully read. Results may be missing.

                      How the analysis runs

                      PCAP and PCAPNG input → TCP stream reconstruction → HTTP/1.x and supported HTTP/2 parsing → field extraction → deterministic rules and optional BiLSTM → masked findings and JSON report.

                      The evidence inspector shows field location, HTTP message, endpoints and detector. It does not explain the model’s internal reasoning. Review the reported limitations and the completeness panel on the Overview page before relying on a result.
